# Level256 Network compatibility investigation

For duplicated Azahar instances, LFCS/account identity collisions, and `0x0026 SignatureInvalid` triage, see [Level256 account identity on cloned Azahar instances](level256-instance-identity.md). The accompanying `tools/level256_identity_audit.py` compares local state without exposing or changing credentials.

## Status

This change does not implement Level256 Network v2 connectivity. No Level256-specific IPC redirect, transport, authentication, or DLP service is enabled in this fork. The existing generic 3GX loader (`plg:ldr`) is separate from Level256's privileged `plg:UDS`/`plg:DLP` services and is not sufficient to run the Level256 network plugin. Enabling it must not be presented as Level256 support.

The historical v1 plugin analyzed below had a recognized 3GX header (`3GX$0002`, flags `0x23`, `CONSOLE_CITRA`) and metadata title `CTRPF - Blank Template` / author `Nanquitas`; its SHA256 was `85e23d71c76869fb2bb3b1be50b2112e0608023301a0f5eaefe3497ed2d965ac`. A separate plugin sample dated 2026-10-22 is analyzed below. User-provided runtime evidence for the historical sample confirms mapping, ARM execution, worker creation, OpenProcess, and the listed memory compatibility paths. It does not establish CTRPF `main`, `PluginMenu::Run`, OSD hook installation/callback, frame event notification, SELECT detection, or rendering.

The menu-display failure is not yet classified. Mapping and ARM execution are distinct from CTRPF initialization and OSD frame delivery. The existing Level256 diagnostics can establish pattern candidates and compare candidate instructions after a later plugin-triggered arbiter call, but those observations alone do not prove an OSD hook callback or SELECT path.

This boundary is intentional: the available v2 public material describes product changes but does not specify the wire protocol, account provisioning, authentication, or the complete IPC contract needed to reimplement its service. A fake success response or invented transport would risk corrupting game state and server accounts.

## Confirmed v2 facts

- The official v2.0.0 update page says the server and network code were rebuilt, accounts are created automatically, v1 and v2 users cannot play together, and stronger anti-cheat was added. It also says a current client version is required.
- The update page describes an installer and Luma3DS custom firmware requirement. This is a console deployment path; it does not establish compatibility with an emulator HLE implementation.
- The public Luma3DS-level256 `SendSyncRequest.c` implements kernel-level session-name redirection for `nwm::UDS` to `plg:UDS`. DLP redirection is conditional on the plugin's `dlpEnabled` state, mapping `dlp:SRVR` to `plg:DLP` and `dlp:FKCL`/`dlp:CLNT` to `plg:FKCL`.
- That source also shows plugin ownership checks by process ID, pause state, IPC command header checks, some command header/buffer descriptor conversions, and NDM/SOC hooks. These are observations from the referenced public source; they do not prove the same protocol is unchanged for v2.

## Existing Azahar components

- `src/core/hle/service/nwm/nwm_uds.cpp` provides the emulator's local UDS implementation and its existing network transport. Replacing it globally would affect local UDS and Pretendo paths.
- `src/core/hle/service/plgldr/plgldr.cpp` registers `plg:ldr` and invokes `Plugin3GXLoader` for configured `.3gx` files. It handles plugin memory allocation/lifecycle and the loader IPC API, not Level256's `plg:UDS` network service.
- `src/core/file_sys/plugin_3gx.cpp` implements the generic 3GX format. It rejects `CONSOLE` compatibility and accepts Citra-compatible variants; this is a platform compatibility check, not a cryptographic signature verifier. No evidence was found that Level256's plugin carries a cryptographic signature that Azahar verifies, and the checked public sources do not document such a signature protocol. Do not claim that the existing check authenticates the official plugin and do not weaken it to load console-only files.
- DLP is implemented independently under `src/core/hle/service/dlp/`; the Level256 DLP endpoints require their own verified IPC behavior and lifecycle.

## Implemented in this revision

- `ProcessServiceRedirect` is an independent process-ID-scoped rules module. It is opt-in and empty by default. For a configured PID it maps `nwm::UDS` to `plg:UDS`; DLP is only mapped when that PID's DLP flag is enabled (`dlp:SRVR` to `plg:DLP`, `dlp:CLNT`/`dlp:FKCL` to `plg:FKCL`). Other process IDs and service names are unchanged.
- `srv:GetServiceHandle` resolves the caller PID from `ctx.ClientThread()->owner_process`. It resolves the selected target before looking up the port. A missing target returns the ordinary service-not-registered error; it does not fall back to the original service. Delayed lookups retain the resolved target. The global service map is never rewritten.
- Guest `srv:RegisterService` can register `plg:UDS` through the existing `ServiceManager` and receives the server-port move handle. The service is tagged with its owner PID; guest unregister requires that PID, and process exit removes that process's registrations. This reuses the guest service registration path, so a separate HLE endpoint is not required just to publish the service name.
- LLE server IPC now has shared `ServerSession::ReceiveRequest` and `ReplyRequest` operations. `svcReplyAndReceive` calls these for command-buffer translation and client wakeup; integration tests can exercise the same Kernel operations without installing an HLE handler.
- Integration tests exercise `srv:RegisterService` → guest ServerPort handle → `Accept` → `srv:GetServiceHandle` → ClientSession `SendSyncRequest` → queued ServerSession request → Kernel receive translation → Kernel reply translation → client wakeup. The response carries a result code and payload. A second test queues multiple A-side lookups before registration and confirms they all wake for `plg:UDS`, while B's ordinary `nwm::UDS` lookup remains pending rather than attaching to the redirected target.
- The redirect state is serialized with the `srv:` HLE service, so a savestate restores the same opt-in state. `Process::Exit()` removes the PID entry, preventing a relaunched process from inheriting it.
- A pure UDS IPC shape translator covers the exact command/header/descriptor-count pairs visible in the public Luma hook. It rejects malformed shapes and unknown commands by returning no translation. It is not connected to request dispatch yet; static-buffer relocation and command-buffer payload rewrites still need a real `plg:UDS` bridge.
- The 3GX loader performs file-range checks for text metadata and sections, uses widened arithmetic for the title-ID list, and safely rejects truncated embedded loader functions. It continues to reject `Compatibility::CONSOLE`.

The internal `SRV::SetLevel256Redirect` API currently has no production caller. There is no Level256 mode toggle exposed to users and no `plg:UDS`, `plg:DLP`, or `plg:FKCL` HLE endpoint. That keeps the incomplete feature default-off. The LLE test uses a guest registered ServerPort with no HLE handler, and a separate regular `nwm::UDS` mock for the unredirected process; it is not an official plugin or production Level256 activation flow.

## Why service redirection is not enabled yet

The public `SendSyncRequest.c` redirects service acquisition inside the kernel hook after `srv:GetServiceHandle` returns a session. It tracks the acquired session name against the calling process and only changes the names for the plugin-owning process; DLP redirection additionally depends on plugin state. Azahar's `SM::SRV::GetServiceHandle` instead looks up a global service name in `ServiceManager` and directly connects the registered port. PID-scoped target selection is now integrated there, and guest `RegisterService` supplies the registered port through standard ServiceManager machinery. This permits actual guest service IPC delivery in the emulator's normal session path, while leaving the global service map unchanged for other processes.

The public Luma `SendSyncRequest.c` source handles `PLGUDS_Initialize` (command 100) by requiring the supplied PID to match the current caller, then stores that PID and log mode in plugin state. `PLGUDS_Finalize` (101) requires the same owner and clears the PID, log mode, signal setting, and DLP flag. `SetPause` (105) and DLP toggle (106) also check the stored owner PID; the latter updates `dlpEnabled`. These observations describe the public hook's state checks, not how the official plugin acquires or registers `plg:UDS`; the test deliberately does not assume that B is the plugin owner.

The source is the public [Level256 Luma `SendSyncRequest.c`](https://github.com/Tekito-256/Luma3DS-level256/blob/master/k11_extension/source/svc/SendSyncRequest.c). In particular, commands 100/101 establish and clear the hook's PID state; they do not themselves call Azahar's or Nintendo's `srv:RegisterService`. The repository source does not establish that the real plugin registers `plg:UDS` as a guest service, so that registration model remains a test fixture only.

The Luma source also rewrites specific IPC header/descriptor layouts before calling the target service and changes NDM/SOC requests. The exact UDS header shapes are represented by a pure tested translator, but that translator is not applied to guest IPC delivery. The LLE test verifies basic command-buffer transfer and response/result propagation through the same Kernel server-session translation methods used by `svcReplyAndReceive`. It does not verify Luma's transformed UDS command buffers, static/mapped buffers, copy/move handles, or error paths. These need a request-forwarding/interception layer that preserves process ownership and session lifecycle. The NDM/SOC rewrites are not implemented.

The Level256-specific enable switch is consequently not exposed yet: there is no verified plugin ownership handshake to call `SetLevel256Redirect`, and no functioning redirect target service. A mode switch at this point would imply a mode that cannot function.

## Build dependency repair

The previous build cache retained `RAPIDJSON=/usr/include/rapidjson`, but that header directory did not exist on this CachyOS environment. The vendored `externals/discord-rpc/CMakeLists.txt` also used `find_file` with names that did not match the directory produced by extracting the pinned RapidJSON archive and did not check download/extraction status. That caused an empty/stale include path and compilation failed at `rapidjson/document.h`.

The dependency remains pinned to the same existing revision. CMake now searches for `rapidjson/document.h` in the pinned extracted include directory, downloads that same archive only when missing, checks download and extraction results, and passes the actual include root to `discord-rpc`. The stale cache entries were cleared during this build; no dependency version was changed.

## Compatibility requirements before implementation

1. Obtain an authoritative v2 IPC/API specification or permission and test vectors from the Level256 maintainers, including exact command IDs, descriptor forms, ownership rules, timeout behavior, and error results.
2. Confirm v2 plugin format/signature requirements and whether the plugin is intended to execute under an emulator. Do not accept unsigned data by weakening existing checks.
3. Add a separately persisted, default-off Level256 option. Only redirect requests from the opted-in title/process; leave ordinary UDS, Pretendo, DLP, CECD, and NDM behavior unchanged otherwise.
4. Implement bounded IPC/buffer validation and explicit unsupported-command errors. Tie socket, event, shared-memory, and worker lifetimes to process/session teardown.
5. Test command translation with published fixtures and test the disabled path against ordinary UDS/Pretendo regression cases before attempting any real-server session.

## Follow-up: GetSystemInfo and plugin startup boundary

The latest user-provided game log confirms that the plugin was mapped for PID 16 / TitleID `0004000000155100` and that ARM execution reached PC `0x070A12D4`. It reports `svc=0x2A GetSystemInfo` but does not contain the call arguments, HLE result, post-SVC register state, later PC, or thread outcome. Targeted diagnostics now capture, for the first `GetSystemInfo` call from the loaded plugin code range and owner PID:

- incoming ABI `Type` (`r1`) and `Param` (`r2`);
- returned `Result` (`r0`) and the 64-bit output value (`r1:r2`);
- the core's PC register value at the end of the HLE SVC handler (`post_hle_pc`), and the plugin thread status before/after the handler;
- at most eight subsequent SVC boundaries on that same thread, with each SVC PC and the preceding handler's `post_hle_pc` value;
- an ARM guest exception only when its PC lies inside the loaded plugin code range and its current process owns that plugin.

This samples execution at SVC boundaries; it is not instruction-level stepping and does not claim to capture every ARM PC transition. A later SVC boundary demonstrates that the thread resumed far enough to execute another SVC. A `Wait*` status identifies a thread that blocked in the observed SVC, and `Dead` after `ExitThread` identifies thread exit. If the thread remains in guest code without another SVC, this bounded trace cannot distinguish a loop from ordinary computation. `Dynarmic` guest exceptions are reported separately with PID, TitleID, thread, status, PC, and exception name. No `GetSystemInfo` result, output value, emulator identity, or guest state is modified.

Azahar's `svc.cpp` maps `GetSystemInfo` type `0x10000` to two Luma-related queries (`REAL_APP_REGION_SIZE` and `IS_N3DS`); type `0x10001` (`NEW_3DS_INFO`) returns success only when the emulated system has four cores, otherwise it returns `ResultInvalidEnumValue`, while its output is currently zero. Other supported types are Azahar's region-memory, kernel-spawned-PID, and emulator-information queries. These are existing HLE behaviors, not evidence that Level256 asks for a particular type. The supplied log omits Type/Param, so no compatibility mismatch can yet be established and none was changed. Public Luma sources demonstrate `svcGetSystemInfo` use for N3DS checks (`type=0x10001`) and Luma-specific information (`type=0x10000`); they do not reveal which query this Level256 plugin issued. [Luma3DS-level256 repository](https://github.com/Tekito-256/Luma3DS-level256), [Luma3DS miscellaneous menu source](https://github.com/LumaTeam/Luma3DS/blob/master/sysmodules/rosalina/source/menus/miscellaneous.c).
